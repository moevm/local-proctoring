# Обновление расширения у пользователей

Текущая версия проекта — [VERSION](../VERSION). Активен только client; отдельный server
не разворачивается. Это инструкция, не публикация архива и не выполненное обновление.
Общий порядок backend / ML / backup / отката:
[production-runbook](../../proctoring/docs/production-upgrade.md).

## 1. Подготовить сервер и контрольную установку

- Основной backend / nginx и ML обновляются первыми. Проверьте key-exchange ML,
  запись на сайте, обработку и просмотр /teach/:id до массовой раздачи расширения.
- В backend/.env должен быть разрешён точный origin
  chrome-extension://nlhjjbgkbfkopkigkbkojpkbffbkeohg в FRONTEND_ORIGINS.
  Сохраните прежние разрешённые origin; изменение требует recreate backend.
- Не отключайте checkOrigin и не разрешайте все chrome-extension origin.
- У расширения нет .env и сервисного ML-ключа. Авторизация — cookie HTTPS-сайта
  в том же профиле Google Chrome, credentials: include.

## 2. Настроить новую папку client

Сохраните существующие video_settings и пользовательские параметры. В client/settings.json:

- session_settings.server_url=https://ВАШ-ДОМЕН/api/remoteSessions;
- server_connection=true для отправки в основной прокторинг;
- local_video_saving=true, если предусмотрен локальный резерв.

В client/manifest.json host_permissions должен разрешать именно https://ВАШ-ДОМЕН/*.
Публичный key не менять: он закрепляет ID независимо от пути распаковки.
Свою версию берите только из своего VERSION:

~~~sh
node scripts/sync-release-version.js
node scripts/check-release-version.js
node --test scripts/tests/releaseVersion.test.js
node --experimental-default-type=module --test client/tests/*.test.js
~~~

В архив включается client, без server, .env, реальных видеозаписей и пользовательских профилей.
На этом этапе архив только подготавливается; распространение выполняется отдельно.

## 3. Обновить без потери OPFS

1. Договоритесь об обновлении вне экзамена / записи / отправки. Служебную вкладку
   во время записи / финализации / upload не закрывать и не обновлять.
2. Завершите запись штатно; дождитесь последнего чанка, финализации и всех скачиваний.
   Проверьте файлы в загрузках, а не только наличие downloadId.
3. Выгрузите все неотправленные записи. Сохраните старую папку client / настройки.
   Не удаляйте расширение и не очищайте профиль, storage.local или OPFS.
4. Обновите файлы существующей распакованной папки. В chrome://extensions нажмите
   «Обновить» у существующего расширения. Проверьте прежний ID.
5. Если раньше был другой ID, сначала обязательна выгрузка всех старых данных:
   они не переносятся в новый ID автоматически. Не заменяйте старую установку до выгрузки.
6. Войдите на production-сайт в том же Chrome-профиле; предоставьте разрешения, если запрошены.
   Обновите сначала одну контрольную установку, затем остальных пользователей.

## 4. Проверить полный цикл

- Запись 20–30 секунд → stop → локальные файлы закончены → отправка → явный успех API.
- На /teach/:id есть камера / экран, оба воспроизводятся; ожидаемые ML-задачи завершились
  и появились события, сводка и снимки. Для сценария без камеры ожидается только экран.
- После потери ответа upload сначала проверяется status/:id. Если videosSaved=true,
  повторно перезаписывать видео нельзя. Ошибка запуска ML решается повтором обработки
  на backend, не новой загрузкой и не ручным удалением локальных оригиналов.
- Ручную форму сайта проверяйте одной парой WebM. Несколько самостоятельных фрагментов
  нельзя склеить через Blob / переименованием; их объединяет прямая отправка расширением.
- Большие записи: upload до 8 GiB на файл / 16 GiB на запрос, ML по умолчанию 4 GiB
  на скачивание; оператор должен согласовать лимиты и свободный диск.

Проверяйте на настоящем HTTPS-домене из пользовательской сети, не только локально.
Не отправляйте пароли / JWT / видео в отчёт. При проблеме сначала сохраняйте файлы;
откат старой папки допустим только вне записи и с тем же ID / неповреждённым OPFS.
Ни старый, ни новый клиент не гарантирует последний чанк при hard-kill Chrome.
