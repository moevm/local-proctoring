# Проверка совместимости с proctoring (15.10.2026)

Изменения относятся только к client. Каталог server не используется и не изменялся.
Основа MV3 / отдельная вкладка записи / OPFS сохранена. Первоначальная проверка
проводилась с версией 2.0.3. Текущая версия комплекта — в [VERSION](../VERSION), manifest генерируется из неё; key и ID сохранены. См. [README](../README.md) и
[CHANGELOG](../CHANGELOG.md). Числа тестов ниже относятся к датам отдельных прогонов.

## Настройка и обновление

1. Сначала обновите backend и nginx основного proctoring.
2. В settings.json задайте session_settings.server_url: https://ВАШ-ДОМЕН/api/remoteSessions.
   Для локального стенда — http://127.0.0.1:8000/api/remoteSessions.
3. В manifest.json host_permissions должен быть разрешён именно этот origin с /*.
   Не добавляйте доступ к произвольным HTTP(S)-сайтам ради обхода авторизации.
4. Публичный key в manifest.json закрепляет общий ID для всех установок из архива,
   независимо от пути распаковки. Публикация в Chrome Web Store не нужна.
   Один раз добавьте в backend/.env основного proctoring разрешённый origin:

   FRONTEND_ORIGINS=chrome-extension://nlhjjbgkbfkopkigkbkojpkbffbkeohg

   Если список уже задан, допишите значение через запятую, сохранив предыдущие.
   Изменение backend/.env требует пересоздания контейнера backend.
   Все chrome-extension:// origin автоматически разрешать нельзя.
   key публичный, не является секретом или доказательством подлинности кода.
   Сохраняйте его неизменным во всех последующих архивах; приватный ключ не нужен.
5. В том же профиле Chrome войдите на сайт прокторинга под владельцем сессии.
   Расширение использует credentials: include; JWT / пароли в настройках хранить не надо.
6. Перед первым обновлением с новым key завершите записи и выгрузите ВСЕ локальные
   видео старой версии. ID изменится, и её OPFS / настройки не перейдут к новому ID.
   Затем загрузите обновлённый client и проверьте ID в chrome://extensions.
   В дальнейшем сохраняйте key и обновляйте без удаления расширения / очистки данных.

Официально поддерживается Chrome 134+. Для offline-записи задайте server_connection=false
и local_video_saving=true, затем выгрузите файлы и загрузите их в отдельную сессию
через форму сайта. При server_connection=true создание серверной сессии требует
работающего соединения и входа на сайт. Не переключайте режим посреди записи.

## Исправленные проблемы

- **Обрыв загрузки при закрытии popup / ложный успех.** Раньше popup запускал fetch,
  а uploadVideo возвращал результат раньше callback chrome.storage.local.get.
  Теперь popup только открывает служебную вкладку, где живёт задача отправки.
  HTTP-ошибки, некорректный JSON и отсутствие явного success/videosSaved не разрешают
  удаление оригиналов.
- **Несовместимая авторизация и MIME.** Передаются cookie входа; файлы OPFS оборачиваются
  в File с video/webm. Собственные host_permissions не заменяют серверный origin allowlist.
  SSE, вызывавший отдельные ошибки доступа / ложные ошибки успешной загрузки, из отправки
  удалён: источником успеха является ответ загрузки, не событие прогресса.
- **Повторная загрузка после потери ответа / ошибки ML.** GET status/:id проверяет,
  сохранены ли видео и запущена ли обработка. Уже сохранённые видео не отправляются
  повторно. При ошибке очереди исходники остаются локально, обработку повторяет преподаватель.
- **Потеря записей при обновлении и по таймеру.** Нет storage.local.clear при смене
  версии; alarm через 245 минут больше не удаляет неотправленные файлы.
  Состояние uploading после перезапуска возвращается в режим восстановления.
- **Потеря / перезапись чанков.** OPFS-записи сериализованы. Остановка ждёт stop,
  последнего dataavailable и завершения всех write/close до чтения размеров и выгрузки.
  Ошибки диска не превращаются в успешное сохранение; проверка квоты теперь ожидается.
- **Отмена скачивания принималась за сохранение.** Скачивание ждёт фактического complete,
  а не выдачи downloadId. interrupted / отмена сохраняют OPFS и метаданные.
- **Проблемы камеры / микрофона.** В файл камеры добавлена дорожка микрофона для ML.
  Отсутствие микрофона не означает отсутствие камеры. Исправлены null-обращения
  при потере экрана в режиме без камеры, закрываются AudioContext и animation loops.
- **Небезопасные уведомления.** Заголовки / сообщения экранируются; имена файлов
  выводятся через textContent. Внутренние страницы записи больше не доступны сайтам
  как web_accessible_resources. Логи ограничены по объёму.
- **Надёжность MV3.** Ответы async runtime messages используют return true и sendResponse;
  не связанные обработчики не перехватывают ответы. unload заменён на pagehide без
  обещания успеть выполнить асинхронную остановку при уничтожении вкладки.
- **Даты и API.** Новые имена / метаданные используют UTC ISO с миллисекундами;
  серверные временные имена не сталкиваются при записи нескольких фрагментов в одну секунду.
  Отчество может быть пустым, а не фиктивным «Без_отчества».
- **Серверная загрузка.** Staging, проверка WebM / видео / длительности, безопасный ffmpeg,
  запрет перезаписи, rollback новых файлов при ошибке БД и videosSaved при ошибке очереди.
  Лимиты согласованы: файл до 8 GiB, запрос до 16 GiB; nginx ожидает обработку до 900 секунд.
  Для больших записей нужно свободное место под временные и результирующие файлы.

## Контракт API

- POST start_session: multipart group, surname, name, title, необязательное patronymic.
  Ответ 201: { id }. Владелец — текущий вошедший пользователь, не присланные ФИО.
- GET status/:id: { videosSaved, processingStarted }; только владелец / разрешённая роль.
- POST upload_video: id, metadata (JSON), screen_video (1+ WebM), camera_video (1+ WebM,
  кроме явно подтверждённого отсутствия камеры), logs (JSON, до 10 MiB).
  Успех: { success: true, videosSaved: true, id }.
  Ошибка очереди: 503 с videosSaved: true; повторная загрузка не нужна.
- GET progress/:id оставлен на сервере для старых клиентов, но новая отправка не зависит от SSE.

## Оставшиеся ограничения

- Закрытие служебной вкладки / убийство Chrome не позволяет гарантировать запись последнего
  ещё не закоммиченного чанка. Восстановление сохраняет уже записанное, но не восстанавливает
  утраченные кадры. Нельзя закрывать служебную вкладку во время записи / выгрузки.
- После прерываний могут остаться несколько файлов на поток. Прямая отправка расширением
  объединяет их на сервере. Ручная форма основного сайта принимает одну пару: несколько
  самостоятельных WebM нельзя просто склеить через Blob / переименовать в один файл.
- Большие записи всё ещё используют keepExistingData при фиксации чанков. Для многочасовой
  записи нужно проверить скорость / свободное место; переход на dedicated OPFS writer
  требует отдельной проверки восстановления после падения, а не замены на один незакрытый
  writable (который может потерять всю запись при сбое).
- Журналы разных extension-контекстов по-прежнему используют read-modify-write одного
  ключа: часть диагностических событий может теряться при одновременной записи.
- Локальный клиент и метаданные не являются доказательством непрерывного контроля:
  владелец браузера может менять расширение / файлы. Сервер проверяет формат и доступ,
  но не удостоверяет подлинность видеосодержимого.
- Сквозной успешный сценарий проверен 16.10.2026 в Google Chrome 154 с отдельным
  профилем, тестовой камерой / микрофоном и настоящим захватом виртуального экрана:
  cookie-вход → создание сессии → запись → stop / финализация OPFS → скачивание →
  отправка через nginx → очистка после ACK → воспроизведение экрана и камеры на
  /teach/:id (1920×1080 и 1280×720, оба HTTP 206, currentTime увеличивается).
  Проверка выявила и устранила на backend отсутствие явного ObjectId при создании
  remote-сессии. Проверены 47 backend-тестов и 14 client-тестов.
  Production-данные не использовались; настройки API менялись только в тестовой копии.
- Отдельного браузерного прогона по-прежнему требуют отсутствие камеры / микрофона,
  аварийное закрытие, popup close при отправке, 401/403, отмена скачивания, сбой ML,
  ручная загрузка, production HTTPS и многочасовая запись. Соответствующие unit-тесты
  не заменяют такой прогон. Последующий прогон 16.10.2026 подтвердил настоящий ML:
  оба задания done, OCR распознал github.com E2E ML TEST, камера вернула отсутствие
  лица за 4.6s. Результаты и оба видео появились на уже открытой /teach/:id без
  перезагрузки. Проверены получение / обновление Bearer по общему ключу и callback
  ошибки, переводящий данные для teach в error при недоступном видео.
  Подробности — docs/ml-end-to-end.md в основном proctoring.

## Автотесты

Node 20.20+:

    node --experimental-default-type=module --test client/tests/*.test.js

Проверяются cookie/MIME, сохранность при ошибке, отсутствие повторного POST, подтверждение
HTTP 200, отмена download, очередь чанков и последний чанк. На backend добавлены тесты
API и реальное объединение коротких WebM через ffmpeg/ffprobe; production-БД не используется.

Источники: [сетевые запросы расширений](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests),
[разрешения](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions),
[async messaging](https://developer.chrome.com/docs/extensions/develop/concepts/messaging).

## Обновления клиента

Перед online-стартом обязателен GET plugin_policy (cookie, no-store, таймаут 10s).
POST start_session передаёт plugin_version из manifest. HTTP 426 означает запрет
новой сессии до обновления; upload / status остаются доступны для старых записей.
Локальные метаданные сохраняют plugin_version записывающего клиента, без замены
при отправке после обновления. Политика и переменные backend описаны в
[контракте веба](../../proctoring/docs/local-proctoring-compatibility.md#политика-обновлений-расширения).
Offline-режим не проверяет серверную политику; номер не является аттестацией клиента.
