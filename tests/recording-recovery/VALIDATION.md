# Проверка 20.10.2026

Google Chrome 154.0.8037.97, headless, отдельный профиль; **8/8**.
Отчёт: [result.json](result.json). Запуск: [README.md](README.md).

- Обрыв начатого HTTP-ответа после приёма multipart: OPFS и uploadAttempt остаются;
  повтор проверяет status, не делает второй POST и завершает очистку.
- Настоящий runtime-обработчик startRecording блокирует продолжение после попытки
  отправки. Дополнительно добавленный новый фрагмент не удаляется при старом ACK.
- Ошибка removeEntry сохраняет индекс/метаданные; повтор завершает очистку.
- Потерянный локальный файл не мешает восстановить ACK уже принятой загрузки.
- Ошибка квоты createWritable при настоящем MediaRecorder сохраняет ранее
  зафиксированный WebM и индекс, финализация сообщает об ошибке.
- Ошибка getFile сохраняет состояние, POST не отправляется.
- Зависание HTTP-ответа и тела JSON завершается timeout без очистки OPFS.
- «Мои записи» показывает файл без индекса, воспроизводит настоящий WebM,
  скачивает непустой файл и оставляет оригинал. После complete доступна кнопка
  «Показать в папке». Открытие системного файлового менеджера в headless не проверялось.

OPFS настоящий; ошибки диска вводятся в соответствующие Chrome API, физический
диск не повреждался. Сетевая потеря и зависания — настоящий локальный HTTP-сервер,
без Playwright route mocks. Это тест восстановления клиента, не повтор полного
production upload / ffmpeg / MongoDB / ML. Проверенные таймауты используют короткое
значение через тот же requestJSON; рабочие значения — 30 секунд / 15 минут.
Ранее зафиксированные данные сохраняются при ошибке записи; это не гарантирует
сохранения последнего чанка при уничтожении Chrome или физической поломке диска.
